# Mayo LiveLinkFace Data — what we actually have

_Last updated 2026-06-17. The Mayo iPhone captures in `data/livelinkface_data/`
are the only in-domain data we have. This documents their real contents, what is
usable, and the preprocessing path that works in the current environment._

## TL;DR
- **23 takes**, **14 usable videos** (RGB `.mov`), **1 duplicate**, **~13 unique**
  patients. The rest are depth-only / metadata-only or a corrupt stub.
- The export is **raw capture**: RGB video + depth + timing log + camera metadata.
  **No ARKit blendshape CSV. No HB labels.** (LiveLinkFace's raw "MySlate" mode
  did not stream blendshapes here.)
- The geometric stream therefore must come from **MediaPipe on the video** (as the
  public sets do) — but MediaPipe has **no installable wheel** in the current
  Python (3.9). The **cached `outputs/mayo_bundles/`** already hold MARLIN +
  MediaPipe features (made by the old `dev` env) for the video takes, so the model
  can run on Mayo from cache.
- A **mediapipe-free MARLIN path** now exists (`src/preprocessing/face_crop_cv2.py`,
  cv2 Haar crop) for re-encoding video in this environment.

## File layout per take
```
<date>_<slate>_<n>/
  <slate>_n_iPhone.mov     # RGB 60fps 720x1280 (only ~15 takes)
  depth_data.bin           # raw depth frames (many takes; 120–320 MB)
  depth_metadata.mhaical   # camera intrinsics + lens distortion (JSON)
  frame_log.csv            # V/D/A frame timing index (NOT blendshapes)
  take.json                # frames, fps, device, date, timecodes
  audio/video_metadata.json, thumbnail.jpg
```

## Per-action segmentation (the design's missing external dependency)
The recordings are **audio-prompted** (the design assumes prompts segment the HB
action sequence). `scripts/mayo_segment.py` recovers structure WITHOUT the
protocol transcript from two signals:
- **Audio prompt onsets** — short-time speech-energy bursts (the spoken prompts).
- **Face motion energy** — abs frame-diff inside the Haar face box (expression
  motion is small vs head motion, so it must be face-localized).

**Honest findings** (full run, `outputs/mayo_segments/`, 15 timelines):
- On clean-audio takes, detected prompt counts are **16–31** (median 17) — far more
  than the ~5–7 canonical HB actions, so audio prompts alone do NOT cleanly map to
  actions (the track includes counting, "relax/good", repeats, ambient talk).
- Detection **degrades on quiet/noisy audio**: FACES020/FACES021 yield only 2–3
  bursts, MySlate_23 yields 9 — a thresholding limit, not "few prompts".
- **2 takes have no audio at all** (MySlate_28, MySlate_29) → motion-only.
- The timeline PNGs confirm **prompt→action structure is real**: face-motion bursts
  follow the prompt windows (visible e.g. in `20260305_FACES018.png`).

Clean, *labeled* per-action segmentation needs the actual protocol/transcript. What
we produce now: per-take **timeline PNGs** + **candidate action windows**
(`outputs/mayo_segments/segments.json`) — the artifact a human can validate/label
against the protocol, and the input for per-action bundle extraction once labels land.

## Encoding path that works here (no mediapipe)
1. `MarlinVideoEncoder.from_default_weights()` + `forward(clip)` — works (MARLIN
   import was decoupled from mediapipe; only the *face crop* needed it).
2. `src/preprocessing/face_crop_cv2.py` — cv2 Haar face crop → 224² → MARLIN,
   streaming only sampled frames (memory-light). Checked against the cached
   MediaPipe-crop embeddings in the **mean-centered** space
   (`scripts/mayo_cv2crop_validate.py`; raw cosine is ~0.99 for any two face clips
   so equivalence must be judged after centering). **Result: rank-1 retrieval 0.80**
   (12/15 takes match their own cached embedding as nearest; same-take centered
   cosine 0.74 vs best-other 0.65). So cv2-crop **preserves most of the per-take
   signal and is a usable mediapipe-free substitute, but it is an approximation,
   not a match** — it is NOT landmark-aligned. Consequence: a "normalized re-encode"
   via cv2-crop would change crop-method AND normalization at once, so it does NOT
   cleanly close the v1-normalized vs Mayo-unnormalized caveat below; that needs
   either mediapipe (to match v1's crop) or retraining v1 on cv2-crop features.

## Severity readout (Run #10 → #11) + GPU (RunPod A100)
`scripts/run10_mayo_severity.py` scores the bundles with v1: latent `s` is
**non-collapsed** (std 1.50), region severities differentiate takes, duplicate takes
score identically. See `docs/archive/experiments/training_runs_pre_v4.md` Run #10.

**Update (2026-06-17, RunPod A100):** MediaPipe is unavailable locally but installs
fine on the pod. We re-extracted all 15 takes with the **REAL MediaPipe FaceLandmarker
+ MARLIN, normalized** to match v1 (`scripts/mayo_extract_pod.py` → `outputs/
mayo_bundles_norm/`) and re-scored (**Run #11**): the result is **essentially identical**
to the un-normalized cached scoring (`s` std 1.50→1.505, ranking preserved) — so the
preprocessing caveat was **immaterial** and the cv2-crop local stopgap is no longer
needed. We also trained an improved GPU warm-start **v2** (attention pooling; eyes
0.38→0.43, mouth 0.82→0.86; `warmstart_v2_attention.pt`) — see Run #12 and
`memory/runpod-gpu.md`. Still: no HB labels → ranking, not metrics.

## What would unlock the most, in order
1. **Clinical HB labels** for these takes (the one true blocker for the HB head).
2. **Protocol transcript / prompt list** → turns the candidate windows into
   labeled per-action clips.
3. **In-domain healthy controls** captured the same way (Run #4's lesson).
4. A **MediaPipe-capable environment** (or port the geometric features to a
   maintained landmarker) to regenerate per-action geometric streams.
